# Docker 应用制包 Skill 设计

日期：2026-07-28

## 1. 背景与范围

本项目最终用于向不能访问公网的内网 Docker 主机交付应用。当前阶段只实现客户端 Codex skill，不设计或实现服务端。

客户端 skill 名称为 `package-docker-app`，源码存放在本仓库的 `skills/package-docker-app/`。验证通过后，可安装或链接到用户的 Codex skills 目录。

skill 接收一个本地项目目录，检查或生成容器配置，收集运行时环境变量和端口映射，按指定平台构建应用镜像，处理 Compose 中引用的第三方镜像，并输出可供后续 Docker Manage 服务端导入的自包含压缩包。

### 1.1 当前目标

- 支持已有 Dockerfile 和 Compose 的单服务或多服务项目。
- 支持缺少 Dockerfile、Compose 或两者都缺少的项目。
- 技术栈不限；固定程序无法识别时，由模型分析代码并向用户消歧。
- 不修改用户现有的 Dockerfile、Compose、env 文件或业务源码。
- 仅处理代码已经明确通过环境变量读取的配置；忽略硬编码配置。
- 支持 Codex 对话交互和独立终端交互。
- 构建指定平台的镜像并生成结构固定、可校验的 `.tar.gz` 制品。

### 1.2 非目标

- 不修改业务代码以消除硬编码配置。
- 不设计服务端上传、镜像导入、Compose 启动、回滚或 LDAP。
- 不在第一版中调用 Docker Manage API 查询已有镜像；该步骤由用户手工完成。
- 不打包 Docker 命名卷中的运行时数据。
- 不对用户 Compose 的能力做安全裁剪。

## 2. 核心设计原则

### 2.1 固定代码主导

Python CLI 是流程和状态的唯一权威实现。文件发现、Compose 解析、变量合并、提问、Docker 命令、制品生成、校验、清理和失败恢复均由固定代码控制。

大模型只处理以下任务：

- 项目缺少 Dockerfile 或 Compose 时，读取代码并生成缺失文件。
- 固定扫描器不能识别的技术栈中，识别明确的环境变量读取和启动入口。
- 启动命令、服务归属或文件选择无法唯一判断时，说明歧义并让用户确认。

大模型不得自行执行一套与 CLI 不同的制包流程，不得修改业务源码，也不得把硬编码值推断为环境变量。

### 2.2 原项目只读

用户原有文件始终只读。skill 的持久文件、临时文件和制品都位于目标项目的 `.docker-manage/` 目录：

```text
.docker-manage/
├── .gitignore
├── generated/
│   ├── Dockerfile
│   └── compose.yaml
├── work/
└── dist/
```

- `generated/` 只保存原项目中缺失、由 skill 生成的基础 Dockerfile 或 Compose。
- `work/` 保存单次执行的计划、答案、部署文件和中间产物，成功、失败或取消后清理。
- `dist/` 保存最终压缩包。
- `.docker-manage/.gitignore` 忽略该目录的生成内容；skill 不修改项目原有 `.gitignore`。

如果项目已有对应文件，`generated/` 中不创建多余副本。部署所需的 Compose 变换只发生在 `work/` 中，最终副本进入压缩包。

### 2.3 明确信任边界

第一版面向单管理员、可信内网。环境变量默认值和最终值，包括密码、Token 和 Key，可以在对话及终端中明文展示，并以明文写入制品 `.env`。CLI 不额外写入调试日志，但 Codex 对话历史、终端记录、压缩包和备份仍可能保存这些值。

`.env`、答案文件和最终制品使用仅当前用户可读写的权限创建。该保护不替代制品传输和存储层的访问控制。

## 3. 组件设计

### 3.1 `SKILL.md`

`SKILL.md` 负责：

- 校验用户给出的目标目录。
- 调用 CLI 获取结构化检查结果和问题列表。
- 仅在 CLI 返回“需要生成”或“需要语义分析”时读取项目代码。
- 把模型生成结果写入 `.docker-manage/generated/`。
- 在对话模式中逐项向用户提问，并把结构化答案交回 CLI。
- 展示 CLI 生成的最终计划，取得确认后启动构建。

### 3.2 Python CLI

Python CLI 提供以下稳定能力：

- `inspect`：发现文件、解析 Compose、扫描已知环境变量用法并输出结构化状态。
- `plan`：合并模型补充信息，生成待回答问题和确定的构建计划。
- `package`：使用答案文件非交互执行构建、导出、校验和打包。
- `run`：在普通终端中完成完整交互，直接回车接受默认值。
- `--dry-run`：完成检查、提问解析和计划生成，但不调用有副作用的 Docker 命令。
- `--non-interactive`：要求提供完整答案文件；存在缺失答案时失败，不等待输入。

所有阶段使用版本化 JSON 状态文件通信。状态文件只存在于单次 `work/` 目录，防止模型输出的自由文本直接控制 Docker 命令。

### 3.3 模型补充协议

模型只能向 CLI 提供受 schema 约束的补充结果：

- 生成文件的路径。
- 项目启动命令和工作目录。
- 源码中明确读取的环境变量名称、默认值、来源位置和所属服务。
- 无法唯一判定的候选项。

CLI 对路径、变量名、服务名和文件存在性重新校验。模型不能通过补充协议注入任意 shell 命令；构建和启动命令只作为 Dockerfile 或 Compose 的结构化字段处理。

## 4. 固定工作流

CLI 使用以下状态机：

```text
检查 -> 分析 -> 等待补充 -> 生成计划 -> 用户确认
     -> 构建 -> 导出 -> 校验 -> 打包
```

### 4.1 预检

开始时检查：

- 目标项目目录存在且可读。
- Docker daemon 可用。
- Docker Compose v2 可用。
- Docker Buildx 可用。
- `.docker-manage/` 可创建且磁盘空间可查询。
- 应用名、版本和目标平台格式合法。

应用名默认使用项目目录名。版本默认使用当前 Git 短提交号；项目不在 Git 中或没有提交时，使用 UTC 时间戳。目标平台默认 `linux/amd64`，用户可改为 `linux/arm64` 或其他 Docker 支持的单一平台。

### 4.2 Docker 文件发现

CLI 查找标准 Dockerfile、Compose 文件名和 Compose override。只有一个明确组合时自动选择；存在多个候选 Dockerfile、基础 Compose、override 或 profile 时，列出候选并要求用户选择。

缺少 Dockerfile 时，模型分析依赖清单、构建方式和启动入口，在 `.docker-manage/generated/Dockerfile` 生成文件。缺少 Compose 时，模型基于选定 Dockerfile 和项目启动方式，在 `.docker-manage/generated/compose.yaml` 生成基础单服务 Compose。任何关键启动信息无法唯一判断时必须询问用户，不能猜测后继续构建。

生成文件通过 CLI 结构校验和 Docker/Compose 校验后才能参与后续流程。

### 4.3 环境变量收集

环境变量候选来自：

- Compose 的 `environment`、`env_file` 和变量插值。
- Dockerfile 的运行时 `ENV`。
- `.env`、`.env.example` 及同类 env 文件。
- 源码中明确的环境变量读取，例如 Python `os.getenv`、Node `process.env`、Spring `${...}`。

CLI 先执行确定性扫描；不能识别的技术栈才请求模型补充。只接受明确的环境变量读取证据，不扫描普通常量并猜测其用途。

候选按服务和容器内变量名合并：

- 所有来源给出的默认值相同，则使用该值作为候选默认值。
- 只有一个来源提供默认值，则使用该值作为候选默认值。
- 多个来源提供不同的非空默认值，则展示全部来源和值，要求用户明确选择或输入新值。
- 即使存在默认值，也必须逐项询问，不得静默接受。
- 不存在默认值时变量为必填，空输入会重新询问。
- 用户输入 `<EMPTY>` 表示显式使用空字符串。
- 密码、Token、Key 等敏感变量与普通变量一样明文展示默认值。

对话模式中，用户回复“默认”接受默认值；独立终端 `run` 模式中，直接回车接受默认值。

最终 Compose 显式把制品变量映射到容器变量，实际值写入根目录 `.env`。多个服务使用同名容器变量但取值不同时，制品变量使用规范化服务名前缀：

```yaml
services:
  web:
    environment:
      PORT: ${WEB_PORT}
```

原 env 文件不会原样进入制品，避免相同变量在多个文件中继续产生优先级歧义。

Dockerfile 中没有默认值的必要构建参数也必须询问。构建参数只用于客户端构建，不自动加入最终运行时 `.env`，除非同名变量同时被服务运行时明确使用。

### 4.4 端口映射

CLI 根据现有 Compose `ports`/`expose`、Dockerfile `EXPOSE` 和可用的镜像元数据收集容器端口。每个服务都允许用户补充未发现的容器端口。

对每个容器端口逐项询问：

1. 是否映射到宿主机。
2. 如果映射，使用哪个宿主机端口。

已有映射作为默认值。用户可以取消原有映射。CLI 在构建前检测制品内重复的宿主机 IP、端口和协议组合，冲突时要求修改。

### 4.5 本地构建服务

包含 `build:` 的服务被视为本地构建服务：

- 构建上下文解析为原项目中的真实路径，即使部署 Compose 位于临时目录也不改变语义。
- CLI 将选定 Dockerfile 临时复制到 `work/`，并生成 Dockerfile 专用 ignore 文件。该文件合并项目现有 `.dockerignore`、原 Dockerfile 专用 ignore 规则，并在末尾强制排除 `.docker-manage/`，防止历史制品和本次中间文件进入构建上下文。原 ignore 文件保持不变。
- 每个服务使用 `docker-manage/<应用名>/<服务名>:<版本>` 形式的新镜像标签。
- 按用户选择的单一目标平台构建并加载到本地 Docker image store。
- 最终部署 Compose 删除 `build:`，只保留确定的 `image:` 和 `platform:`。
- 交叉架构构建缺少 QEMU、builder 或平台支持时立即失败，并给出缺失能力，不生成最终制品。

### 4.6 第三方镜像

只有 `image:`、不含 `build:` 的服务被视为第三方镜像服务。每个不同镜像逐项暂停并提示用户在 Docker Manage 中查询可复用镜像：

- 用户粘贴服务器已有镜像名：校验镜像引用格式，写入最终 Compose，并记录为服务器外部依赖；客户端不拉取、不打包该镜像。
- 用户选择“打包”：保留原镜像名，使用本机 Docker 登录状态按目标平台拉取，并加入制品。

第一版不自动访问 Docker Manage，也不验证用户粘贴的服务器镜像是否实际存在或平台是否匹配。最终计划和 manifest 必须明确列出这些外部依赖。

### 4.7 本地文件依赖

CLI 解析 Compose bind mount、`configs.file`、`secrets.file` 和其他明确的本地文件引用：

- 解析后位于项目目录内的相对路径复制到制品 `files/`，部署 Compose 改写为制品内相对路径。
- 指向项目外的路径、绝对路径或解析后逃出项目目录的符号链接不得自动复制。逐项要求用户选择“按服务器路径原样保留”或“终止制包”。
- 选择保留的服务器路径写入 manifest 的宿主机路径依赖列表。
- Docker 命名卷保持不变，不导出其现有数据。

复制前展示每个路径及估算大小；最终计划展示文件依赖总大小。复制目录时始终排除其中的 `.docker-manage/`，避免把工具工作目录递归装入自身制品。文件复制保留运行所需权限，但不得在归档中创建逃出制品根目录的路径。

### 4.8 计划确认

任何耗时构建或拉取发生前，CLI 展示并保存确定计划：

- 应用名、版本、Compose 项目名和目标平台。
- 使用的 Dockerfile、Compose 和构建上下文。
- 每个服务的最终镜像名。
- 需要本地构建、拉取打包和服务器复用的镜像。
- 环境变量最终值及来源。
- 端口映射。
- 随包复制的文件和保留的服务器路径。
- 预计磁盘占用；无法准确估算的部分明确标记为未知。

用户明确确认后才进入构建状态。取消时清理 `work/`，不执行 Docker 构建或拉取。

## 5. Compose 规范化与校验

Compose 必须使用结构化 YAML 解析和写入，不使用字符串替换。最终部署 Compose：

- 不包含任何 `build:`。
- 所有服务都有确定的 `image:`。
- 运行时环境变量从制品 `.env` 显式注入。
- 端口、网络、命名卷、健康检查、依赖关系、restart 策略和用户未要求改变的字段保持语义不变。
- 本地相对文件路径改写为制品内路径。
- 服务器绝对路径仅在用户明确确认后保留。

写入后执行等价于以下命令的校验：

```text
docker compose --env-file .env -f compose.yaml config
```

校验失败必须终止，不允许以警告方式继续。

## 6. 制品格式

输出路径为：

```text
.docker-manage/dist/<应用名>-<版本>.tar.gz
```

归档根目录包含：

```text
manifest.json
compose.yaml
.env
images.tar
checksums.sha256
files/
```

- `images.tar` 通过一次 `docker image save` 保存所有本地构建及需要传输的第三方镜像，使公共镜像层只保存一次。没有任何需要传输的镜像时可省略该文件，并在 manifest 中记录空列表。
- `files/` 只在存在随包文件依赖时创建。
- `checksums.sha256` 覆盖除其自身之外的所有归档文件。
- 外层使用 gzip 压缩，兼顾通用性和内网传输体积。

`manifest.json` 至少包含：

- 制品 schema 版本。
- 应用名、版本、Compose 项目名、目标平台和创建时间。
- 每个服务的最终镜像引用。
- 已打包镜像的引用、ID、digest、平台和归档状态。
- 依赖的服务器既有镜像。
- 保留的服务器宿主机路径。
- payload 文件的大小和 SHA-256，不包含 `manifest.json` 和 `checksums.sha256` 自身。
- 生成该制品的 CLI 版本。

CLI 在压缩前验证每个已打包镜像的平台与目标平台一致。压缩完成后重新打开归档，验证路径安全、文件清单和校验和。最终文件先使用同目录临时名称写入，所有检查通过后原子重命名；失败时不留下看似完整的目标文件。

## 7. 失败与清理

以下情况立即失败：

- Docker、Compose 或 Buildx 不可用。
- 必填答案缺失或格式非法。
- Docker 文件生成后仍无法通过校验。
- 宿主机端口冲突。
- 构建、跨平台加载、镜像拉取或保存失败。
- 本地文件无法读取或违反项目路径规则。
- 磁盘空间不足。
- Compose、manifest、归档路径或校验和检查失败。

失败时：

- 删除本次 `work/`、临时归档和不完整输出。
- 保留 `.docker-manage/generated/`，便于用户检查模型生成文件。
- 不删除执行前已经存在的 Docker 镜像。
- 对本次新建镜像默认不自动删除，以免误删被其他标签或项目复用的层；在错误信息中列出可选清理对象。
- 返回阶段、失败命令的安全摘要和可执行的修复建议。

## 8. 测试策略

### 8.1 脱离 Codex 的测试

绝大部分能力必须能在没有 Codex 的环境中验证：

- Python 单元测试覆盖文件发现、Compose 规范化、变量合并、默认值冲突、服务变量命名、端口、镜像分类、路径安全、manifest 和校验和。
- 使用注入到 `PATH` 的假 Docker 可执行文件做集成测试，记录参数并模拟成功、失败和平台信息。
- `--dry-run --non-interactive` 配合答案文件在 CI 中运行完整计划流程。
- 最小示例项目执行真实 Docker 冒烟测试：构建、保存、解包、校验、删除测试镜像后重新加载。真实 Docker 测试可用明确标记在无 daemon 的 CI 中跳过。
- 使用 skill creator 的 `quick_validate.py` 校验 skill 目录、frontmatter 和命名。

### 8.2 模型边界测试

为“缺少 Dockerfile/Compose”和“未知技术栈环境变量扫描”准备固定项目样例。测试使用预先保存、符合 schema 的模型补充结果恢复 CLI 流程，以证明模型与固定程序之间的契约无需 Codex 也可测试。

模型是否能针对新的任意项目正确生成文件，必须在 skill 安装到 Codex 后做行为验收。该测试不替代 CLI 的确定性测试。

### 8.3 必须覆盖的场景

- 无 Docker 文件、只缺 Dockerfile、只缺 Compose。
- 已有单服务和多服务 Compose，且原文件内容和时间戳不变化。
- 多个 Dockerfile、Compose override 和 profile 的选择。
- 环境变量有默认值、无默认值、显式空值和来源冲突。
- 多服务同名环境变量取相同值和不同值。
- 密码与 Key 默认值明文展示并正确写入 `.env`。
- 端口保留、修改、取消和冲突。
- 第三方镜像由服务器复用和由客户端拉取打包。
- 项目内文件依赖、项目外路径、绝对路径和逃逸符号链接。
- `linux/amd64`、`linux/arm64` 和跨平台失败。
- 任一步骤失败或取消时不产生最终制品。
- 解包后的 Compose 可通过校验，镜像归档可重新加载。

## 9. 验收标准

实现完成需要同时满足：

1. 用户可通过 Codex skill 对话完成整个流程，使用“默认”接受默认值。
2. 用户可在普通终端运行 CLI，直接回车接受默认值。
3. 标准已有 Docker 配置的项目无需模型语义分析即可完成制包。
4. 原项目已有文件在成功、失败和取消流程中均不发生变化。
5. 缺失文件只生成到 `.docker-manage/generated/`，并经过固定程序校验。
6. 最终制品包含可部署 Compose、完整 `.env`、必要镜像、本地文件依赖、manifest 和校验和。
7. 所有自动化测试通过，真实 Docker 冒烟测试在具备 daemon 的开发环境中通过。
8. skill 通过 `quick_validate.py`，并在 Codex 中完成至少一次缺失 Docker 文件项目的行为验收。

# Docker 应用重复打包快速流程设计

日期：2026-08-11

## 目标

首次打包继续执行完整问询和计划确认。项目已经完整成功打包过时，复用 CLI 保存的当前环境变量与端口快照，一次性展示全部问题的默认答案，只询问用户是否修改；答案完整后直接生成计划并开始打包，不再等待第二次计划确认。

## 重复打包判定

仅当项目中以下两个路径都存在且都是普通文件时，进入重复打包模式：

- `.docker-manage/.env`
- `.docker-manage/ports.json`

CLI 只在完整成功打包后一起更新这两个快照，因此二者同时存在表示有一组可复用的成功配置。只存在其中一个、任一路径不是普通文件，或 `inspect` 报告快照无效时，不得把它当作可复用配置；前两种情况执行首次打包流程，快照无效时按 CLI 错误停止。

不从 `.docker-manage/work/<run_id>/state.json`、旧答案 JSON 或历史归档推断重复打包状态。

## 交互流程

### 首次打包

保留现有行为：

- 环境变量按稀疏覆盖格式询问。
- 非环境变量问题逐项处理。
- 第三方镜像必须单独提醒并等待选择。
- 计划生成后完整展示，等待用户明确确认，再调用 `package`。

### 重复打包

`inspect` 成功后，把所有问题按 CLI 顺序放进同一份编号清单。每项展示问题 ID、中文提示、当前配置、声明默认值、最终默认答案、来源、可选值及中文含义；密码、Token 和 Key 仍完整显示。第三方镜像继续使用醒目的 `【重要】` 提示，bind mount 继续完整显示路径、位置、大小、稳定部署路径和归档行为。

清单只发起一次修改询问：

```text
如需修改，请回复“序号: 值”；全部沿用以上默认答案请回复“无修改”。
```

处理规则：

- `无修改` 表示用户明确接受清单中全部默认答案，包括第三方镜像和 bind mount 的默认处理方式。
- 用户可提交一个或多个 `序号: 值`，未提交的项目自动采用清单中展示的默认答案。
- `<EMPTY>` 继续表示显式空字符串。
- 重复序号、越界序号、非数字序号、缺少冒号或不在选项内的值必须指出具体错误。
- 必填问题没有默认值时，在清单中明确标记“必填，无默认值”；即使用户回复 `无修改`，也只追问这些缺失项。
- 用户修改后若仍有缺失或无效答案，只追问对应项，不重新询问已确定答案。

模型把最终选择展开为包含每个已回答问题 ID 的完整私有答案 JSON，继续使用现有机器协议和 `0600` 权限。

## 计划与自动打包

重复打包模式仍必须调用 `plan`，并完整展示计划与 CLI 返回的 `plan_hash`。计划展示是进度和审计输出，不是新的用户确认点。

只要 `plan` 退出码为 `0`，模型立即调用 `package`，把 CLI 返回的精确 `plan_hash` 传给 `--confirm-plan-hash`。该哈希仍负责在 Docker 发生变化前阻止检查结果、答案或计划被篡改；跳过的是第二次人工确认，不是计划生成、哈希校验或 CLI 安全边界。

以下情况不得自动进入 `package`：

- `plan` 返回答案缺失、答案无效或其他非零退出码。
- CLI 返回的计划没有 `plan_hash`。
- 用户在回答修改问题时选择 `abort` 或明确要求停止。
- 运行所依据的 `run_id`、答案文件、平台或 profiles 无法保持一致。

首次打包仍要求计划确认。重复打包中即使用户提交了修改，完成这一次配置问询后也直接执行计划和打包，不再增加计划确认。

## 实现范围

本次只修改 `skills/package-docker-app/SKILL.md` 及其契约测试：

- 在工作流开始处定义首次/重复打包分支。
- 把现有环境变量和非环境变量问询规则保留为首次打包流程。
- 增加重复打包的全量默认清单、稀疏修改和缺失回退规则。
- 把计划确认改成条件行为：首次打包等待确认，重复打包展示后立即执行。

不修改 CLI、问题模型、答案 JSON 格式、快照格式、计划哈希、Docker 操作和归档结构。`inspect` 已提供当前值、默认值、来源和选项，现有 CLI 能接受展开后的完整答案并校验计划哈希，因此无需新增协议。

## 测试

先用不包含新规则的现有 skill 对重复打包场景做基线测试，确认代理仍逐项问询或在计划后等待第二次确认。修改后用同类场景验证：

- 两个快照同时存在时，代理进入重复打包模式。
- 只存在一个快照时，代理执行首次打包流程。
- 重复打包一次性展示所有默认答案并只问是否修改。
- `无修改` 展开全部有默认值的问题。
- 无默认值问题仍被追问，不能被猜测或遗漏。
- 重复打包计划展示后立即调用 `package`，首次打包仍等待确认。
- 第三方镜像警告、bind mount 细节、完整敏感值显示及精确 `plan_hash` 传递保持不变。

同步更新 `tests/unit/test_skill_contract.py`，用正向契约断言固定分支判定、一次修改询问、缺失回退和条件式计划确认。最后运行契约测试、完整测试套件和 skill 校验。

## 完成标准

- 首次打包交互没有减少。
- 只有两个当前配置快照都存在时才启用重复打包快速流程。
- 重复打包最多只有一次常规用户确认；仅缺失或无效答案会触发补问。
- 重复打包仍完整生成并展示计划，但不等待计划确认。
- CLI 的答案校验、计划哈希和 Docker 安全边界保持有效。
- 契约测试、完整测试套件和 skill 校验通过。
